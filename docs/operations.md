## Requirements

- Docker Engine 24+ with Compose v2 (`docker compose version`).
- 2 vCPU and 2 GB of RAM are enough for a team; PostgreSQL holds everything durable.
- For production: a host name pointing at the server, ports 80 and 443 reachable (certificates are
  obtained automatically), and an e-mail provider (Resend or an SMTP relay with TLS).

## Local stack

```bash
cp .env.example .env     # optional: add a DeepSeek key, e-mail or OAuth credentials
scripts/gen-secrets      # writes every internal secret to .env (never overwrites)
docker compose up -d     # postgres, valkey, mailpit, migrate, seed, api, worker, web
```

| What | Where |
|---|---|
| Interface | http://localhost:8080 |
| Demo account | `demo@gouvra.dev`, password = `DEMO_PASSWORD` in `.env` (labelled *Demo*) |
| E-mails sent by the app (Mailpit) | http://localhost:8025 |
| API reference | http://localhost:8080/api/docs |
| API (direct, used by OAuth callbacks in development) | http://localhost:8000 |

The `migrate` service applies database migrations and exits; `seed` creates the demo account
once (idempotent). Without `DEEPSEEK_API_KEY` the demo uses only the offline scripted model.

`docker compose down` stops the stack and keeps the data; `docker compose down -v` erases it.

## Configuration

All settings are environment variables, documented in [`.env.example`](../.env.example).
`docker compose` passes each one explicitly to the containers (nothing else from `.env` leaks in).

| Variable | Purpose |
|---|---|
| `SESSION_SECRET`, `ENCRYPTION_KEYS`, `POSTGRES_PASSWORD`, `VALKEY_PASSWORD`, `SANDBOX_TOKEN`, `DEMO_PASSWORD` | Generated by `scripts/gen-secrets`. |
| `APP_URL` | Public URL of the interface (links in e-mails, origin checks). |
| `API_PUBLIC_URL` | URL browsers use to reach the API — OAuth callbacks are built from it. Production: same as `APP_URL`. |
| `EMAIL_PROVIDER` | `resend`, `smtp` or `console` (development only). |
| `RESEND_API_KEY`, `EMAIL_FROM` | Resend delivery and sender address (a verified domain). |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_SECURITY` | SMTP relay; production requires `starttls` or `ssl`. |
| `GITHUB_CLIENT_ID/SECRET`, `GOOGLE_CLIENT_ID/SECRET` | Optional OAuth sign-in. A button only appears when its pair is set. Callback URLs: `${API_PUBLIC_URL}/api/v1/auth/oauth/{github,google}/callback`. |
| `DEEPSEEK_API_KEY` | Used by the demo seed and the real-provider tests. Workspaces store their own keys, encrypted. |
| `BILLING_PROVIDER`, `STRIPE_*` | Billing (Stripe test or live mode); `none` disables billing. |
| `SIGNUP_ENABLED` | `false` closes public sign-up (invitations still work). |

Check a configuration without revealing any value:

```bash
docker compose run --rm api gouvra check-config          # presence and format
docker compose run --rm api gouvra check-config --live   # plus a read-only call to each provider
```

## Production

[`docker-compose.prod.yml`](../docker-compose.prod.yml) runs the same images with:

- **Caddy** as the only published service: automatic HTTPS (Let's Encrypt / ZeroSSL), HTTP→HTTPS
  redirect, HSTS, a strict Content-Security-Policy, HTTP/3; it serves the interface and proxies
  `/api` on the same origin (no CORS, `SameSite` cookies).
- **API and worker as separate processes** (executions, e-mails and evaluations never run in the API).
- **PostgreSQL and Valkey on a network without outside access**; persistent volumes for data and
  certificates; JSON logs rotated by Docker.

```bash
cp .env.example .env && scripts/gen-secrets
# In .env: DOMAIN=gouvra.example.com  ACME_EMAIL=ops@example.com  APP_URL=https://gouvra.example.com
#          EMAIL_PROVIDER + its credentials, EMAIL_FROM, and optionally OAuth / provider keys
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml run --rm api gouvra create-superadmin you@example.com
```

The API refuses to start in production with an unsafe configuration (insecure cookies, a
non-HTTPS `APP_URL`, console or unencrypted e-mail, missing secrets).

Use `COMPOSE_FILE=docker-compose.prod.yml` (or `-f docker-compose.prod.yml`) with every command of
this guide when operating the production stack.

## Backups and restores

```bash
scripts/backup                                  # → backups/gouvra-<UTC timestamp>.dump
scripts/restore backups/gouvra-<stamp>.dump     # asks before replacing the data
COMPOSE_FILE=docker-compose.prod.yml scripts/backup
```

- The dump is PostgreSQL's compressed custom format; each backup is verified (`pg_restore --list`)
  right after it is written, and files are readable by their owner only.
- PostgreSQL holds everything durable. Valkey only carries the queue wake-ups, rate limits and live
  streams: it needs no backup.
- **Keep `ENCRYPTION_KEYS` with your backups, but stored separately**: provider keys and tool
  credentials are encrypted in the database and cannot be read without the key ring.
- Schedule backups with cron or a systemd timer, e.g. daily:
  `0 3 * * * cd /srv/gouvra && COMPOSE_FILE=docker-compose.prod.yml scripts/backup && find backups -mtime +14 -delete`
- `scripts/restore` stops the API and the worker, restores in a single transaction, applies any
  newer migrations and restarts them. Test restores regularly (for instance into a staging host).

## Rotating secrets

**Encryption key ring** (protects provider keys and tool credentials at rest):

```bash
scripts/gen-secrets --rotate-encryption-key     # prepends a new key to ENCRYPTION_KEYS in .env
docker compose up -d api worker                  # the new key encrypts; old keys still decrypt
docker compose run --rm api gouvra rotate-secrets   # re-encrypts every stored secret with the new key
# then remove the old key from ENCRYPTION_KEYS and restart api and worker
```

**Session secret** (`SESSION_SECRET` signs CSRF and OAuth-state cookies): replace it with
`scripts/gen-secrets --print`, restart; open pages simply fetch a new CSRF token.

**Database and Valkey passwords**: change the password inside the service first
(`ALTER USER gouvra PASSWORD '…'` / `CONFIG SET requirepass …`), then in `.env`, then restart.

**Provider keys** belong to workspaces: replace them from *Providers*; the old value is erased.

## Upgrading

```bash
scripts/backup
git pull                      # or check out the release tag
docker compose -f docker-compose.prod.yml up -d --build
```

The `migrate` service applies schema migrations before the API and the worker start (they wait
for it). `/readyz` reports `migrations: up_to_date` once done. Read the `CHANGELOG.md` entry of the
release before upgrading. To roll back: restore the backup taken before the upgrade, then start
the previous version (or, when the release notes allow it, `gouvra migrate --down <revision>`
before starting the previous images).

## Monitoring and diagnosis

| Endpoint | Meaning |
|---|---|
| `GET /healthz` | The API process answers (liveness). |
| `GET /readyz` | Database reachable with migrations up to date, Valkey reachable (readiness). |

- Logs are JSON on stdout (`docker compose logs -f api worker`), one `request_id` per request,
  returned to clients in errors as a diagnostic ID; secrets and personal data are redacted.
- The worker writes a heartbeat file checked by its container health check; executions whose
  worker disappeared are failed with `worker_lost` (retryable) after their lease expires.
- Failed executions explain themselves in the interface (cause, next action, error code) — the
  server logs are not needed for everyday diagnosis.

## Administration commands

Run inside the API image: `docker compose run --rm api gouvra <command>`.

| Command | Purpose |
|---|---|
| `migrate [revision] [--down]` | Apply database migrations (run automatically by the `migrate` service); `--down <revision>` or `-1` rolls back explicitly. |
| `check-config [--live]` | Verify the configuration without printing any value. |
| `create-superadmin <email>` | Grant instance administration to an existing account. |
| `rotate-secrets` | Re-encrypt stored secrets with the first key of `ENCRYPTION_KEYS`. |
| `seed-demo [--offline]` | Create the labelled demo account and workspace (idempotent). |
| `export-openapi --output <file>` | Write the OpenAPI document (`docs/api/openapi.json`). |
