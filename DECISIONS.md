# DECISIONS — Gouvra

Chaque choix technique ou produit, avec sa raison. Le plus récent en bas de chaque section.
Priorité en cas de conflit : `BRIEF.md` > `docs/ui.md` / `docs/conception.md` > préférences.

## Produit

- **D-001 — Nom : Gouvra.** Du français *gouverner* (« gouverner un navire » = tenir la barre ; *gouvernail*, *gouverne*), lui-même du latin *gubernare* et du grec *kybernân* : « piloter ». En anglais, la même racine donne *govern* / *governance* — double sens utile : on pilote ses agents et on les gouverne (permissions, budgets, quotas). 6 lettres, 2 syllabes, se prononce « gou-vra » / « GOO-vruh ». Vérifié le 2026-10-11 : aucun produit tech connu à ce nom (recherche web), et `gouvra` est libre sur npm, PyPI, GitHub (utilisateur/organisation), `gouvra.com`, `gouvra.dev`, `gouvra.io` (requêtes RDAP Verisign / Google Registry / Identity Digital → 404). Écartés : Aileron, Timon, Auriga, Pitwall, Kelpie (noms pris partout), Octant (outil VMware), Nacelle (plateforme e-commerce), Diriga/Navarq (comptes GitHub pris).
- **D-002 — « AgentHub » remplacé partout** par Gouvra (code, UI, logo, docs, packages, images Docker). Les documents de cadrage convertis (`docs/conception.md`, `docs/ui.md`) gardent leur contenu ; un bandeau en tête rappelle que « AgentHub » était le nom de travail.
- **D-003 — Workspace = organisation (tenant).** Un utilisateur appartient à plusieurs workspaces ; la facturation, les quotas, les budgets et la rétention s'appliquent au workspace. « Administration multi-organisation » = panneau super-admin qui gère tous les workspaces et utilisateurs de l'instance.
- **D-004 — Langue de l'interface : anglais par défaut + français complet**, i18n dès le départ (i18next, textes dans `web/src/locales/*.json`). Détection de la langue du navigateur, choix mémorisé dans le profil. E-mails transactionnels dans la langue de l'utilisateur.
- **D-005 — Licence Apache-2.0.** Permissive (adoption, contributions), avec concession de brevets explicite ; compatible avec toutes les dépendances retenues (MIT/BSD/Apache). Le module SaaS fait partie du dépôt mais reste désactivé par défaut en auto-hébergement (`BILLING_PROVIDER=none`).
- **D-006 — Thème clair par défaut, sombre disponible** (choix mémorisé côté serveur dans les préférences + `localStorage` pour éviter le flash au chargement).
- **D-007 — Densité : modérée-élevée** (outil pour développeurs), hiérarchie typographique nette, texte courant 14 px, jamais sous 12 px.

## Architecture

- **D-010 — Monolithe modulaire + worker séparé** (même code Python, deux points d'entrée), conformément à `conception.md` §7. Pas de microservices. Un troisième processus, `sandbox`, n'exécute que du code non fiable dans des conteneurs éphémères (voir D-035).
- **D-011 — Backend : Python 3.13, FastAPI, Pydantic v2, SQLAlchemy 2 (async) + asyncpg, Alembic.** Stack de `conception.md`. SQLAlchemy 2 typé + Alembic = migrations versionnées et réversibles.
- **D-012 — File d'exécution sur PostgreSQL (`FOR UPDATE SKIP LOCKED`) plutôt que Celery.** Raisons : (1) la mise en file est transactionnelle avec la création de l'exécution (jamais d'exécution « créée mais pas en file ») ; (2) le moteur est 100 % asyncio, mal servi par Celery ; (3) il faut des limites de concurrence *par workspace*, l'annulation d'une tâche en cours et des planifications définies par les utilisateurs — aucune file générique ne le fait sans contournements. Même conception que Solid Queue (Rails 8), River (Go) ou Oban (Elixir) : bail (lease) + heartbeat, récupération des exécutions orphelines, réveil par `LISTEN/NOTIFY`. Redis (Valkey) sert au rate limiting, au relais temps réel (pub/sub pour SSE et deltas de tokens) et aux signaux d'annulation rapides.
- **D-013 — Valkey 8 au lieu de Redis ≥ 7.4.** Redis 7.4+ n'est plus sous licence open source OSI ; Valkey (BSD-3, Linux Foundation) est compatible protocole et client (`redis-py`).
- **D-014 — PostgreSQL 17.**
- **D-015 — Moteur d'agents maison, léger, derrière une interface `ModelGateway`.** Comparaison (preuve de concept papier, `conception.md` §17) : LangGraph, PydanticAI, OpenAI Agents SDK. Tous imposent leurs propres abstractions de modèle et de boucle, ce qui gêne trois exigences centrales : tracer *chaque* appel de modèle/outil avec tokens et coût normalisés, appliquer des limites strictes (étapes, appels d'outils, tokens, coût, durée) et annuler proprement. Une boucle d'appel d'outils maison (~500 lignes, testée) garde le contrôle total et n'enferme dans aucun fournisseur.
- **D-016 — Adaptateurs de modèles :** `openai_compatible` (générique, réutilisable), `deepseek` (préréglage du précédent, API officielle, testé en réel), `anthropic` (API Messages native), `test` (déterministe, scripté, sans réseau). Normalisation des messages, des appels d'outils, de l'usage et des erreurs.
- **D-017 — Coût : trois sources explicites** — `provider_reported` (le fournisseur renvoie un coût), `estimated` (tokens × tarif du registre de modèles, avec date et source du tarif), `unavailable` (tarif inconnu : jamais de zéro trompeur).
- **D-018 — Temps réel : SSE** (`text/event-stream`) avec reprise via `Last-Event-ID` (rejoue les événements persistés, puis s'abonne au pub/sub). Plus simple que WebSocket, traverse les proxys, suffisant (flux serveur → client).
- **D-019 — API `/api/v1`** : collections imbriquées sous le workspace (`/workspaces/{id}/agents`), ressources unitaires à la racine (`/agents/{id}`, `/executions/{id}`), comme proposé dans `conception.md` §13. Erreurs au format RFC 9457 (Problem Details) + `code` stable + `request_id`. Pagination par curseur opaque. Idempotence via l'en-tête `Idempotency-Key` sur les créations.
- **D-020 — Contrôle d'accès central** : un seul module (`gouvra/core/authz.py`) résout l'acteur (session ou clé de service), charge la ressource *filtrée par workspace* et applique une matrice rôle → permissions. Ressource d'un autre workspace = **404** (jamais 403, pour ne rien révéler). Rôles : owner > admin > member > viewer.
- **D-021 — Sessions serveur** (jeton aléatoire 256 bits en cookie `HttpOnly; Secure; SameSite=Lax`, seul son SHA-256 est stocké), rotation à la connexion, à l'élévation de privilège et périodiquement ; expiration glissante + absolue ; révocation par session. **CSRF** : double soumission (cookie lisible + en-tête `X-CSRF-Token`) + vérification d'`Origin` sur les méthodes non sûres.
- **D-022 — Mots de passe : Argon2id** (`argon2-cffi`, paramètres RFC 9106 « second choix » : m=64 Mio, t=3, p=4), rehash automatique si les paramètres changent.
- **D-023 — Secrets fournisseurs : AES-256-GCM**, clé hors base (`ENCRYPTION_KEYS`, trousseau `kid:clé` pour la rotation), données associées = workspace + ressource (un chiffré ne peut pas être déplacé vers un autre workspace). Seuls les 4 derniers caractères sont conservés en clair pour l'affichage. Rotation documentée dans `docs/operations.md`.
- **D-024 — Logs JSON structurés (`structlog`)** avec `request_id` / `execution_id` de corrélation et un filtre de rédaction (clés sensibles, motifs de jetons, e-mails).
- **D-025 — E-mails : interface `EmailSender`** avec adaptateurs `resend` (production), `smtp` (Mailpit en dev) et `console`. Choix par `EMAIL_PROVIDER`.
- **D-026 — Paiement : interface `BillingProvider`** avec adaptateurs `stripe` (mode test fourni) et `simulated` ; `none` en auto-hébergement.

## Frontend

- **D-030 — React 19 + TypeScript strict + Vite**, React Router 7, TanStack Query 5 (seule source des données serveur), Tailwind CSS 4 (tokens en variables CSS, thème sombre par tokens sémantiques), primitives accessibles Radix UI (composants possédés, approche shadcn), **Motion** pour l'animation (layout, AnimatePresence, `reducedMotion="user"`), Lucide pour les icônes, React Hook Form + Zod, TanStack Virtual pour les longues traces, React Flow (`@xyflow/react`) pour l'éditeur de workflows, Recharts pour les graphiques, CodeMirror 6 pour JSON. Polices Inter + JetBrains Mono auto-hébergées (`@fontsource-variable`), aucun CDN tiers.
- **D-031 — Client API typé généré depuis l'OpenAPI** (`openapi-typescript` + `openapi-fetch`) : le contrat front/back est vérifié par le compilateur.

## Exécution des outils

- **D-035 — Bac à sable** : les outils « code » s'exécutent dans un conteneur éphémère (`--network none` par défaut, système de fichiers en lecture seule, `tmpfs`, utilisateur non root, `cap-drop ALL`, `no-new-privileges`, limites CPU/mémoire/PIDs, délai). Seul le service `sandbox` parle au démon Docker, et seulement via un proxy de socket filtrant. Jamais dans l'API ni dans le worker.
- **D-036 — Outils intégrés sûrs** (exécutés dans le worker, sans code utilisateur) : requête HTTP vers hôtes autorisés (protection SSRF : résolution DNS vérifiée, IP privées interdites), calculatrice (analyseur d'expressions, pas d'`eval`), horloge/fuseaux, JSON (extraction de chemin), texte (stats/regex bornée), UUID, aléatoire.

## Identité (phase 2)

- **D-060 — Inscription non énumérable.** `POST /auth/register` répond toujours 202 « vérifiez votre boîte ». Si l'adresse existe déjà, aucun compte n'est créé et le titulaire reçoit un e-mail « quelqu'un a tenté de s'inscrire avec votre adresse ». Le lien de vérification connecte l'utilisateur (preuve de possession de l'adresse), ce qui évite tout oracle « compte créé / pas créé ».
- **D-061 — Connexion possible avant vérification**, mais toute route hors `/auth/*` et `/me` renvoie 403 `email_not_verified` : l'écran D guide l'utilisateur.
- **D-062 — Jeton CSRF lié à la session** (HMAC-SHA256 de l'empreinte de session avec `SESSION_SECRET`, « signed double-submit cookie » OWASP) + vérification d'`Origin` sur toute requête non sûre portant des cookies, y compris login/register (anti « login CSRF »). Cookies préfixés `__Host-` quand `COOKIE_SECURE=true`.
- **D-063 — Rotation de session** toutes les 12 h d'activité, à la connexion et au changement de mot de passe ; l'ancien jeton reste valable 60 s pour les requêtes déjà en vol. Expiration glissante 72 h, absolue 30 jours.
- **D-064 — Liens e-mail avec jeton dans le fragment d'URL** (`/reset-password#token=…`) : jamais envoyé aux serveurs, absent des journaux d'accès et des en-têtes Referer.
- **D-065 — Invitation acceptée uniquement par le compte dont l'e-mail vérifié correspond** à l'adresse invitée (un lien transféré ne donne pas accès).
- **D-066 — Liaison OAuth** : une identité GitHub/Google à e-mail vérifié se lie au compte de même adresse ; si ce compte n'était pas vérifié, son mot de passe est supprimé et ses sessions révoquées (empêche la prise de compte par pré-inscription).
- **D-067 — Politique de mot de passe (NIST 800-63B)** : 10 à 128 caractères, refus des mots de passe courants et de ceux qui reprennent l'adresse e-mail, pas de règles de composition arbitraires.

## Agents, outils, exécutions (phase 3)

- **D-070 — SDK officiel `anthropic` pour l'adaptateur Anthropic** (référence Claude API : projet Python ⇒ SDK, pas de HTTP brut). Les autres fournisseurs passent par `httpx`. Modèles Claude du registre et tarifs : table officielle mise en cache le 2026-10-06 ; prix de cache non publiés estimés (0,1× lecture, 1,25× écriture), signalés dans les notes du registre.
- **D-071 — Réflexion (« reasoning ») neutre côté produit** : `auto | off | low | medium | high | max`, traduit par adaptateur (DeepSeek `thinking` + `reasoning_effort` ; Claude `thinking: adaptive` + `output_config.effort`, `between_tools` ou effort bas quand le modèle ne permet pas de la couper). Les blocs de réflexion Claude et le `reasoning_content` DeepSeek sont rejoués tels quels au tour suivant (vérifié en réel sur DeepSeek).
- **D-072 — Tarification DeepSeek heures pleines / creuses** (01–04 h et 06–10 h UTC en semaine, sinon −50 %) appliquée à l'horodatage de chaque appel ; jours fériés chinois non modélisés (coût surestimé ces jours-là, toujours étiqueté « estimé »).
- **D-073 — Validation stricte des arguments d'outils** : JSON Schema 2020-12, objets fermés par défaut (`additionalProperties: false` implicite), références distantes refusées, schéma ≤ 32 Ko. Une erreur d'outil est renvoyée au modèle (il peut se corriger) et tracée.
- **D-074 — Outils HTTP durcis contre le SSRF** : liste d'hôtes autorisés, hôte figé (les gabarits ne remplacent que chemin et requête, valeurs encodées), résolution DNS vérifiée puis **connexion épinglée sur l'IP contrôlée** (SNI et `Host` conservés) contre le DNS rebinding, redirections revalidées à chaque saut, ports 80/443/8080/8443, réponse plafonnée. Réseaux privés interdits sauf `HTTP_TOOL_ALLOW_PRIVATE_NETWORKS=true` (auto-hébergement de confiance).
- **D-075 — Numérotation des événements par la base** (`UPDATE … SET last_event_seq = last_event_seq + 1 RETURNING`) : l'API et le worker écrivent dans la même trace sans collision ; l'état terminal et son événement sont commités ensemble.
- **D-076 — Fragments de jetons non persistés** : diffusés en direct (Valkey pub/sub → SSE), regroupés toutes les 60 ms ; la réponse complète du modèle est l'enregistrement de référence.
- **D-077 — Annulation** : en file ⇒ annulée immédiatement ; en cours ⇒ drapeau + événement dans une transaction, puis `NOTIFY` au worker qui annule la tâche asyncio ; filet de sécurité par lecture du drapeau à chaque tour et au battement de cœur.
- **D-078 — Récupération des exécutions orphelines** : bail de 45 s renouvelé toutes les 10 s ; un « reaper » marque `failed / worker_lost (retryable)` les exécutions dont le bail a expiré. Arrêt du worker : 30 s pour finir, puis `worker_shutdown`.
- **D-079 — Idempotence des lancements** : `Idempotency-Key` unique par workspace pendant 24 h ; même requête ⇒ 200 avec l'exécution d'origine, requête différente ⇒ 422 `idempotency_mismatch`.
- **D-080 — Adaptateur de test scripté** (`gouvra-test-1`) piloté par directives (`[tool:…]`, `[fail:…]`, `[sleep:…]`, `[json]`, `[think]`) : déterministe, hors réseau, utilisé par les tests, la CI, les E2E et la démo hors ligne. Son coût est « indisponible » (aucun faux prix).

## Évaluations (phase 6)

- **D-081 — Un cas = une exécution ordinaire** (déclencheur `evaluation`, priorité −1) : même moteur, mêmes traces, coûts, limites, quotas et concurrence qu'en production. Une évaluation ne contourne jamais les garde-fous.
- **D-082 — Variantes sans nouvelle version** : modèle, fournisseur et instructions peuvent être surchargés pour un run seulement (`config_overrides` sur l'exécution, annoncés dans l'événement `execution.started`). L'historique des versions de l'agent reste propre ; un fournisseur d'un autre workspace est refusé (422) et ignoré par le moteur.
- **D-083 — Critères** : exact (normalisé), contient (tous / au moins un / aucun, score partiel), regex (bibliothèque `regex`, délai 0,5 s contre le ReDoS, motif ≤ 500 caractères), JSON Schema 2020-12, juge LLM (réponse JSON, score 0–1 ou 0–10, réflexion coupée). Un cas réussit si tous les critères passent et si le score pondéré atteint le seuil. Un critère qui ne peut pas s'exécuter rend le cas « en erreur » : jamais de verdict deviné.
- **D-084 — Critère par défaut** : égalité avec la réponse attendue (texte) ou « contient » (JSON attendu) ; sans attendu ni critère, le cas est « en erreur : no_graders » plutôt que réussi en silence.
- **D-085 — Appels du juge comptés à part** (`usage.kind = judge`, `judge_cost_amount`) : le coût de l'agent évalué reste comparable d'un run à l'autre.
- **D-086 — Comparaison** : cas appariés par identifiant (même suite) ou par nom (suites différentes) ; « amélioré / régressé » si le verdict bascule ou si le score bouge d'au moins 0,05.
- **D-087 — Directive `[score:X]` du modèle scripté** : juge déterministe pour les tests et la démo hors ligne.
- **D-088 — Garde-fous d'isolation lus dans OpenAPI** : FastAPI 0.143 ne met plus à plat les routeurs inclus, ce qui avait vidé en silence l'ancien garde-fou (il ne vérifiait plus rien). Il lit désormais la table des routes publiée, échoue si elle paraît vide, et couvre aussi les routes par ressource.

## Interface des phases 2 à 4

- **D-089 — Contrat OpenAPI exact** : les schémas de réponse marquent obligatoires les champs à valeur par défaut (`json_schema_serialization_defaults_required`), les types web sont générés avec `--default-non-nullable false` : en entrée, les champs par défaut restent facultatifs ; en sortie, ils sont garantis. Le compilateur vérifie le contrat dans les deux sens.
- **D-090 — Compteurs d'usage jamais masqués** : le filtre de secrets masquait `input_tokens` & co (la clé contient « token »). Les compteurs connus sont exemptés ; tout le reste qui ressemble à un secret reste masqué.
- **D-091 — Trace en direct** : exécution en cours ⇒ SSE (rejeu puis événements, fragments de texte, reprise par Last-Event-ID) ; exécution terminée ⇒ lecture REST de la trace. Les compteurs se rafraîchissent au plus toutes les 500 ms ; le flux du workspace anime les listes (ligne qui s'illumine au changement d'état).
- **D-092 — Un coût n'est jamais un nombre nu** : « ≈ » si estimé, icône « communiqué par le fournisseur » sinon, « — » (jamais 0 $) si indisponible, « + » si partiel ; la provenance est lisible au clavier et par lecteur d'écran.
- **D-093 — Formulaires en dialogue remontés à chaque ouverture** (clé de session) plutôt que réinitialisés dans un effet : conforme aux règles du compilateur React, aucun état résiduel d'une ouverture à l'autre.
- **D-094 — Lignes de liste en container queries** : une même ligne d'exécution s'adapte à la largeur de sa liste (pleine page, vue d'ensemble, détail d'agent), pas à celle de la fenêtre.
- **D-095 — Référence E2E = build de production** (Caddy, port 8080) ; le serveur de dev ne sert qu'à itérer. Les parcours lisent les vrais e-mails dans Mailpit et exécutent les vrais agents via le worker (modèle scripté hors ligne).

## Stabilisation (phase 5)

- **D-096 — Langues chargées à la demande** : chaque langue est un chunk récupéré avant le premier affichage (pas de clés visibles) ; une langue prise en charge n'a pas de repli (les deux sont complètes), toute autre langue retombe sur l'anglais. Chunk principal : 547 → 232 Ko.
- **D-097 — Trace virtualisée au-delà de 120 éléments** (TanStack Virtual, lignes mesurées), avec suivi automatique du dernier pas tant que l'utilisateur n'a pas remonté ; en dessous, chaque événement garde son animation d'entrée.
- **D-098 — Référence API auto-hébergée** : Swagger UI 5.33.1 (`swagger-ui-dist`, Apache-2.0) est embarqué dans l'API, servi sous une CSP « scripts de même origine uniquement » ; ReDoc (CDN) est retiré. Aucune ressource tierce n'est chargée par le produit.
- **D-099 — Production** : Caddy est le seul service publié (HTTPS automatique, HSTS, HTTP/3) et sert l'interface et l'API sur la même origine ; PostgreSQL et Valkey sont sur un réseau interne sans accès extérieur ; conteneurs en lecture seule, sans capacité Linux ni élévation de privilèges ; port de santé interne pour Caddy.
- **D-100 — SMTP authentifié et chiffré** (`SMTP_SECURITY` starttls/ssl), refusé en clair en production ; Resend refusé sans clé.
- **D-101 — Sauvegardes** au format personnalisé de `pg_dump`, vérifiées juste après l'écriture ; la restauration arrête les écrivains, restaure en une transaction, migre puis redémarre. `ENCRYPTION_KEYS` se conserve à part.
- **D-102 — Illustrations animées décoratives exclues d'axe** (`data-decorative`, `aria-hidden`, décrites par une phrase) : leur texte fictif passe par des fondus ; tout le reste de l'interface reste audité.
- **D-103 — Une migration commitée n'est jamais modifiée** (leçon de l'incident de la phase 6) ; une correction devient une nouvelle migration. Le retour arrière est explicite : `gouvra migrate --down <révision>` ou `-1`.
- **D-104 — Comparaison d'évaluations orientée verdict** : une phrase (« la candidate fait mieux / moins bien / pareil ») avant les chiffres ; deltas colorés selon le sens utile (un coût ou une durée qui baisse est une amélioration) ; la plus ancienne des deux exécutions sélectionnées sert de référence.
- **D-105 — Workflows : graphe acyclique, orchestrateur en machine à états dans PostgreSQL.** Un run est verrouillé (`FOR UPDATE SKIP LOCKED`), ses étapes terminées sont soldées, puis le graphe est parcouru une fois dans l'ordre topologique. Une étape attend que toutes ses entrées soient soldées et s'exécute si au moins un lien est actif (source réussie, bonne branche d'une condition, ou échec toléré par `on_error: continue`), sinon elle est sautée : les jointures après une condition fonctionnent sans configuration. Une condition laisse passer la valeur qu'elle a testée vers la branche choisie (comme un aiguillage) : une étape placée après elle reçoit la donnée, pas « vrai/faux ». Les étapes « agent » sont des exécutions ordinaires (même file, mêmes limites, même trace) liées au run ; les outils s'exécutent hors verrou. Réveils : fin d'exécution, résultat d'outil, annulation (NOTIFY), et revérification au plus tard toutes les 30 s ou à l'échéance.
- **D-106 — Pas de langage d'expression dans les workflows** : des gabarits `{{input.x}}`, `{{steps.id.output|json|status|error}}` vérifiés à l'édition (référence inconnue ou étape qui ne s'exécute pas avant = erreur), et des conditions à opérateurs fermés (regex bornée dans le temps). Rien à injecter, rien à évaluer.
- **D-107 — Suivi en direct par instantanés** : chaque avancée publie l'état complet du run (≤ 60 étapes) ; un spectateur qui se reconnecte ne perd rien, sans numéros de séquence à rejouer. Le détail d'une étape « agent » réutilise le flux de son exécution.
- **D-108 — Brouillon à concurrence optimiste** : chaque sauvegarde cite la révision dont elle part (409 sinon) ; publier fige une version immuable ; un run fige le graphe exécuté. Un run de brouillon exige le droit d'édition.
- **D-109 — Noms de schémas uniques dans le contrat OpenAPI** : jamais de nom qualifié par module (`gouvra__…`) ; les schémas des workflows sont préfixés `Workflow…`, ceux de l'usage renommés.
- **D-110 — Bac à sable : mise en œuvre.** Service `gouvra sandbox` (même image, processus et conteneur distincts) avec ses propres réglages `SANDBOX_*` : il ne reçoit aucun secret de l'application. Le code et les arguments passent par l'environnement du conteneur (base64, ≤ 50 Ko / 64 Ko), le wrapper les efface avant d'appeler `main(args)` et renvoie le résultat JSON après un marqueur aléatoire par exécution : aucun volume, aucun fichier à copier, racine en lecture seule. Images d'exécution figées (`python:3.13.15-alpine3.24`, `node:24.21.0-alpine3.24`), téléchargées au démarrage ; tant qu'elles manquent, l'outil répond « en préparation » au lieu de bloquer. Le réseau n'est possible que si l'instance l'autorise **et** que l'outil le demande. Les conteneurs portent une étiquette d'expiration : seul ce qui a expiré est nettoyé (plusieurs instances peuvent partager un démon).
- **D-111 — `docker-socket-proxy` (Tecnativa v0.5.0)** entre le bac à sable et Docker : seules les sections conteneurs et images sont ouvertes ; le proxy lui-même tourne en lecture seule, sans capacité. Risque résiduel documenté dans `docs/security-review.md` (l'API conteneurs reste puissante) ; gVisor (`SANDBOX_RUNTIME=runsc`) ou Docker rootless pour aller plus loin.
- **D-112 — Éditeur de workflows : React Flow (@xyflow/react 12), chargé seulement par les pages workflows.** Le graphe JSON est la seule source de vérité ; le canevas en est une vue. Accessibilité : chaque étape a un nom (type, nom, état, problèmes), les libellés de React Flow sont traduits, et tout ce qui se fait à la souris se fait aussi au clavier (sélection au clavier, liens et suppression depuis le panneau de propriétés, liste des étapes sur la page de run).
- **D-113 — Sauvegarde automatique (≈ 0,7 s) plutôt qu'un bouton « Enregistrer »** : chaque modification part avec la révision dont elle découle (409 = conflit visible, rien n'est écrasé) ; un glisser ou une saisie dans un même champ forment une seule étape d'annulation ; la sauvegarde en attente est forcée avant un test, une publication ou en quittant la page.
- **D-114 — Le run se lit sur le graphe** : l'état de chaque étape est dessiné sur son nœud, le chemin pris en vert, les branches non prises estompées, le lien vers l'étape active animé (désactivé si « réduire les animations ») ; une liste ordonnée des étapes double le graphe pour la lecture et le clavier.
- **D-115 — Un seul lanceur pour tous les déclencheurs d'automatisation** (planification, webhook, « exécuter maintenant », test) : chaque déclenchement est enregistré (*fire*) avec son issue et le run lancé ; les mêmes garde-fous qu'un lancement manuel s'appliquent (concurrence, limites de débit, quotas). Acteur dédié « automation “nom” » dans l'audit ; un lancement manuel garde la personne qui a cliqué.
- **D-116 — Planificateur dans PostgreSQL** : verrou `SKIP LOCKED` sur les planifications échues, prochaine échéance calculée et **validée avant** le lancement (un lancement en échec ne rejoue jamais le tick), tick manqué tiré une fois en retard (jamais en rafale), chevauchement « sauter » par défaut pour les planifications, « autoriser » pour les webhooks (un évènement ne se perd pas), pause automatique après 5 échecs consécutifs. `croniter`, cinq champs + macros, fuseaux IANA (heure d'été incluse).
- **D-117 — Signature des webhooks à la Stripe** : `Gouvra-Signature: t=…,v1=HMAC-SHA256(secret, "t.corps")`, fenêtre de 5 min, comparaison à temps constant, plusieurs `v1` acceptés ; idempotence par identifiant de livraison explicite, sinon par la requête signée elle-même ; format GitHub (`X-Hub-Signature-256` + `X-GitHub-Delivery` obligatoire) pour brancher GitHub directement. Adresse = jeton aléatoire de 192 bits (pas l'identifiant de l'automatisation).
- **D-118 — Connecteurs définis dans le code, pas par configuration** : chaque opération a un schéma fermé et construit sa requête côté serveur ; les identifiants (un document JSON scellé par connexion) ne quittent jamais le serveur ; les opérations deviennent des outils `kind: connector` gérés par leur connexion (schéma non modifiable, archivés à la suppression). Bibliothèque initiale : Slack, Discord, GitHub, webhook sortant signé.
- **D-119 — Registre = vue de gouvernance agrégée côté serveur** (modèles du catalogue avec prix publiés, fournisseurs configurés, agents qui les utilisent ; outils de l'espace et intégrés disponibles), plutôt qu'une nouvelle source de vérité.
- **D-120 — Interface des automatisations** : préréglages d'horaires (la plupart des gens n'écrivent jamais de cron) et expression traduite en clair (cronstrue 3.27, EN/FR) avec les prochains runs calculés par le serveur ; secret de webhook montré une seule fois dans une fenêtre qu'on ferme volontairement ; exemples de signature générés avec la vraie adresse ; journal des livraisons rafraîchi toutes les 4 s (refus compris, avec leur raison).
